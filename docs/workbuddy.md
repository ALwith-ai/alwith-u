# ALwith 与自己的 WorkBuddy

更新：2026-09-15。状态：已确认的产品目标，不代表所有能力已经交付。"能力怎么交付"一节写的是当前实现选择，不是唯一允许的实现。

## 目标与供给

人人都能做自己的 WorkBuddy。用户指挥编程 Agent 写自己的 UI、增加自己的业务能力，不重写底座。

| 类别 | ALwith 提供 | 用户的工作 |
| --- | --- | --- |
| CLI／执行器 | 成熟 CLI＋适配器，自带模型、工具、Skills、MCP 能力，可替换执行器 | 默认直接用，需要时换 CLI，不要求重写执行器或其配置体系 |
| Runtime | 闭源运行底座，托管执行器、模块、通信和运行态 | 直接使用协议与客户端 |
| 完整聊天组件 | 消息流、输入、工具展示、审批、历史、滚动与恢复 | 直接复用复杂交互，允许调整或替换，不强制采用 |
| QA | 测试管理、执行、结果与证据能力 | 按需接入 |
| Gamepad | 手柄输入、映射和控制能力 | 按需接入，不要求安装整个 Desktop |
| alwith.dev | 产品定义、研发、测试、构建与交付体系，可调用 QA | 按需采用，不要求所有 WorkBuddy 遵循研发流程 |
| 统一账号体系，含宠物 | 登录、账号权益、宠物资产及购买能力；宠物是平台收入来源，接账号就具备，不另列为可选模块 | 不写认证，不架账号服务器，不重建宠物交易与权益系统 |
| 统一移动端 | 同一个手机应用访问多个 WorkBuddy，提供连接、聊天、审批和历史入口 | 不为每个 WorkBuddy 另写、部署、维护手机 App |
| 应用 UI 参考 | ALwith U 完整参考源码，展示如何组成可运行应用 | 自己写品牌、首页、导航、设置、布局和业务页面；用不用 shadcn、选择什么 UI 技术由用户决定 |
| 自己的业务能力 | 接入规范、工具接口与示例 | 增加自己的数据接入、工具、模块和业务逻辑 |
| 开发发行 | 协议、客户端包、文档、测试与构建发行工具 | 编程 Agent 按文档实现，用户确认效果并验收 |

普通导航、设置和布局不是强制共享组件。复杂聊天应有整套成品可用，不能让用户重做；选择另一 UI 技术仍能通过协议接能力，但不承诺 React 组件直接运行在所有框架上。

## 完整应用与能力分开

| 同级独立应用 | WorkBuddy 形态 |
| --- | --- |
| ALwith U | 聊天型，也是完整参考应用 |
| ALwith Board | 画布、多模态创作型 |
| ALwith Desktop | 综合桌面型，可组合 QA、Gamepad、alwith.dev 等能力 |
| 用户自己的 WorkBuddy | 自己的 UI＋选用的 ALwith 能力＋自己的业务能力 |

QA、Gamepad、alwith.dev 是能力，不是与 U 平级的完整应用。QA 可由 alwith.dev 使用，也可被应用单独采用；当前是否同包不决定产品层级。

Board 纳入讨论，是承认它本身就是 WorkBuddy 变种，不是要求拆画布组件、拆短剧模块，不是并入 Desktop，也不是塞进 Runtime。

## 平台公共服务边界

| 事项 | 规则与原因 |
| --- | --- |
| 账号 | 一个 ALwith 账号使用自己创建或获授权的多个 WorkBuddy，避免每个客户重复建设认证。账号在平台服务器；应用通过公共 Auth 接入。Runtime 不是账号服务器，当前也尚未实施平台身份校验 |
| 宠物 | 随账号接入，资产与权益跨应用一致，是平台收入来源；不意味着全部免费，也不意味着每个窗口必须显示。定价、付费规则、展示交互与接口另定 |
| 移动端 | 一个移动端选择、访问不同 WorkBuddy，不为每个客户复制一套手机应用 |
| 登录态 | 同一 ALwith 账号，应用独立登录：U 与 Desktop 各自在应用数据目录保存服务器签发的 token，独立刷新与退出；不共享、复制或迁移凭据。宠物和权益按服务端用户 ID 归属 |
| 执行位置 | 手机连接运行 Runtime 的桌面或服务器。三种情况分开说：窗口隐藏时会话继续（现有）；桌面应用退出后是否继续，取决于 Runtime 是随应用 spawn 还是用户级常驻进程（常驻是决策里的入口形态，尚未实现，不是现有保证）；独立部署在服务器上的 Runtime 与桌面无关。不自动同步任意业务页面 |
| 两种登录 | ALwith 平台登录与 CLI／模型供应商认证分开，不能相互冒充 |

## 普通用户制作流程

| 步骤 | 用户 | 编程 Agent |
| --- | --- | --- |
| 开始 | 选择自己使用的编程 Agent，提供 ALwith 文档入口和需求 | 阅读文档、参考 ALwith U、获取获授权发行物 |
| 实现 | 描述 UI、业务数据和允许的操作 | 创建独立工程，复用现成能力，写 UI 和业务代码 |
| 迭代 | 看效果，用自然语言提出修改 | 在原工程上修改并测试，不反复重建底座 |
| 验收发行 | 用真实工作检查结果、审批和历史 | 提供验证结果，完成打包与发行配置 |
| 使用 | 安装自己的 WorkBuddy，通过统一移动端访问 | 后续按用户指令维护 |

开场示例：“阅读 ALwith 文档，参考 ALwith U，复用已有组件和能力，帮我做一个自己的 WorkBuddy。我要这样的 UI，以及这些业务功能……”

不要求用户必须在 U 内制作，不要求 U 改写自身；U 是参考，不是强制父框架。

## 能力怎么交付

ALwith 自己的能力以**包**交付，应用在依赖清单里声明，像任何 crate 或 npm 包一样链接；官方包限定进程侧 Rust、界面侧 TS（决策，不限制用户自己的业务代码用什么）。平台服务（账号、移动端）不是包，是服务。

包里带 `alwith-module.json` 和可执行入口的是**模块**：Runtime 按应用的清单把它 spawn 成子进程，应用经 `modules/<name>/<method>` 调它、收它的事件。哪些能力做成模块进程、哪些做成库，按它是否需要独立于应用运行来定，是实现选择，可以变。

当前的选择：

| 能力 | 当前形态 | 现状 |
| --- | --- | --- |
| alwith.dev | 模块进程 | 编排状态在模块里；它起 Agent 也经 Runtime，不自己 spawn |
| 多供应商 | Runtime 原生管理＋CLI 适配库 | Desktop／浏览器提交选择，Runtime 读取凭据并调用适配器；不依赖文件、存储或 QA 服务启用 |
| QA、git、shell | 各自的共享 Rust 库＋Runtime 内置协议服务 | QA 包含 Maestro；不再有混合的 `alwith-host` 库或 Web 专用 host 进程；Desktop 保留原生 QA 凭据薄适配 |
| 文件、命名存储 | `alwith-modules` 中的 `alwith-fs`／`alwith-store` 库 | 已迁出 Desktop；Runtime 可独立提供协议服务，Desktop 继续直接复用需要的库 |
| 聊天组件 | TS 包 | 界面侧代码 |
| Gamepad | Desktop 内的能力 | 目标是其他 WorkBuddy 也能选用，抽包未做 |

Runtime 内置服务与模块进程分开：前者随同一个 Runtime 二进制提供，stdio／WS 共用，按配置启用；后者才有模块清单与独立进程。供应商选择、凭据解析和能力探测归 Runtime；CLI 参数与环境翻译归适配器；alwith.dev 的执行者默认值、工具白名单和插件隔离归模块。拆库不新增常驻进程。CLI 原生历史仍由 CLI／适配器提供，不因这次迁移新建会话库。Runtime 的平台登录仍未实现，不能把文件服务接通当作完整产品验收。

QA 平台凭据由 Desktop 提供是已接受的业务边界，不是待消除的架构耦合，也不要求迁入 Runtime。独立服务器可以运行 Runtime；若启用需要平台凭据的 QA 功能，应接入对应凭据提供方，缺失时明确报错，不阻塞其他能力。QA 平台凭据与 Runtime 管理的模型供应商凭据不是同一项职责。

平台 Auth 由公共 `@alwith/module-auth` TS 包和 `alwith-module-auth` Rust 库提供，不属于 Runtime 核心，也不属于 CLI／模型供应商认证。Desktop 的 QA 凭据适配仍由 Desktop 提供。U 复用登录接口、账号状态、token 存储契约与 Rust 刷新合并逻辑；JSON 凭据留在各应用自己的数据目录，未改为 Rust 私有凭据库，未迁移 Desktop 登录。U 已接邮箱验证码／密码登录、注册和账号设置；OAuth 尚未接入，现有 Desktop 深链不能直接复用。开发环境接 api-dev，正式构建接 api。服务器是否允许同账号多登录会话、同账号宠物权益的端到端一致性仍需实际联调，不将前端接线当作完整验收。

外部 U 构建不链接私有 Auth 或应用发现 crate：`@alwith/native` 通过 npm 分发预编译动态库，U 只保留薄 ABI 调用层。内部 Desktop 仍可直接复用同一份 Rust 实现；这不是复制两份认证逻辑，也没有将认证迁入 Runtime。具体发行平台与验证结果见 [原生分发说明](native-distribution.md)。

模块对界面侧的类型随包一起给：模块包自带 `types.ts`（从 Rust 类型生成），应用界面从包里 import。应用的进程侧是否链接模块的 Rust crate、是否需要 Rust 合同类型，按实际消费者定；Desktop 目前把模块载荷按 JSON 过界，是当前选择，不是规则。

## 保密与技术边界

- Runtime 与需要保护的能力维持私有实现，通过获授权的接口与产物交付；纳入体系不等于开源。
- U 的许可不自动覆盖 Runtime、客户端、QA、Gamepad、alwith.dev 或 Board；逐项明确使用、修改和再分发权利，保留第三方条款。本轮不修改许可证、不发布。
- 不强制每项能力对应一个 crate、仓库或进程；只有需要独立运行的才做成模块进程。产品归类不替代生命周期、原生能力与发行设计。
- 平台允许换 CLI，不代表本轮要求 U 支持所有执行器。Codex 仍拥有原生会话，不另建可写的权威会话库。
- 记录同步不扩成代码、环境或运行任务迁移；历史查看与原生续聊分别验收。

## Rust 依赖与进程边界

Runtime 统一托管 Agent，不意味着所有业务能力只能通过 RPC 调用。判断依据是实际运行与数据所有权，不是 Cargo 依赖图是否“干净”。

| 问题 | 决定与原因 |
| --- | --- |
| Desktop 能否依赖 alwith-dev crate | 可以。私有 Desktop 复用私有 Rust 库本身合法合理；编译依赖不等于启动第二套编排或 Agent。当前 Desktop 按用途链接 QA、git、shell 等能力库，自举调用走 Runtime；这是当前实现选择，不是以后禁止依赖 alwith-dev |
| 何时调整依赖 | 查到重复实现、重复运行编排、绕过 Runtime 托管 Agent、私有实现泄露或客户构建必须取得私有源码时，按具体调用用途修正 |
| 能力库复用 | 直接依赖实际承担职责的库，避免经混合 host 库中转；不能据此要求所有 alwith-dev 引用清零 |
| DTO 合同层 | 确实是跨进程合同或需要独立复用时抽取；不为清空依赖图而增加合同 crate。界面侧类型走模块包的 `types.ts`，Rust 侧是否需要合同类型按消费者定 |
| QA 的独立性 | QA 是可选业务能力，不自动意味着独立 crate、二进制或进程 |
| 内部与外部 | 官方私有应用可以复用私有库；外部客户应只凭获授权的发行物构建，不需要 ALwith 私有源码。两种要求不矛盾 |

禁止把“src-tauri 没有 alwith_dev::”“Desktop Cargo 依赖图没有 alwith-dev”“所有 alwith.dev 函数必须走 RPC”设为架构完成门禁。真正门禁是：实现不重复、运行所有权唯一、无第二套 Agent 托管、协议与原有行为保持、私有源码不泄露、外部发行物可独立使用。

本结论不反向要求把现有 RPC 改回库调用，也不证明当前每条依赖都必要；修改前仍须检查具体用途与行为。

## 验收

| 维度 | 标准 |
| --- | --- |
| 开发者 | 外人只凭获授权的 CLI／适配器、Runtime、客户端、组件、ALwith U 参考和文档，一周做出能安装、登录、聊天、审批、看历史的独立 WorkBuddy，不依赖维护者私有源码或本机路径 |
| 普通用户 | 无编程基础的人只描述 UI 与业务、检查效果，即可指挥 Agent 完成同一流程，不用自己实现聊天、认证或移动端 |
| 平台 | 同一账号分别登录两个不同 WorkBuddy，宠物权益一致，统一移动端可切换 |

上述完整产品验收尚未完成。2026-09-15 的 host 重构已验证 Runtime 内置服务的 stdio／WS 请求、路径拒绝、监听隔离与断线释放；这不替代登录、宠物或移动端验收。后续见 [实施计划](plans/2026-09-13-restructure.md)。
